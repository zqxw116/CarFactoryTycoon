## 1. 게임 개요

자동차 공장 자동화 **방치형/클리커/공장 운영 게임**.

- **시점**: ISO(아이소메트릭)
- **라인 구조**: 화면 상단 1라인 → 하단 5라인으로 이어지는 **S자 컨베이어벨트**
- **핵심 딜레마**: 라인 속도↑ → 생산량↑ 이지만 로봇팔 체결이 못 따라가 **체결 누락** 발생 → 테스트 구간에서 불량 처리. 유저 클릭/AI NPC/자동화로 보완하며 *속도·체결안정성·수익·자동화*의 균형을 맞추는 게임.

### 라인 구성
1. **1라인 프레임 조립** (스캔/용접)
2. **2라인 도장** (프라이머/색상/코팅, 부스 진입 시 재질·색 변경)
3. **3라인 내부 조립** (시트/문/창문)
4. **4라인 외부 조립** (엔진/보닛/바퀴, 리프트 연출)
5. **5라인 테스트** (방수→압력→고속주행→판매대기, 누락 시 불량 연출)

### 차량 기준 치수
- 차량 길이 큐브 기준 **scale X=2, Z=4.5**
- 로봇팔은 라인별 파츠 개수만큼 **4.5m(차량 길이) 간격**으로 배치

## 2. 체결 시스템 설계 (확정)

### 판정 = IK 도달 게이트 (2026-06-18 재변경)
- 스테이션 **트리거 콜라이더**는 "후보 진입 감지"용(작업 대상 선정). 콜라이더는 라인 앞쪽에 둬서 차량이 일찍 닿으면 로봇팔이 미리 체결 준비.
- **실제 체결 진행 조건**: 로봇팔 끝 `Rig_End`(= `RoboticArmIK.endEffector`)와 파츠 `ArmLookTarget`(= `AssemblyPart.armLookTarget`)의 거리 ≤ `assembleReachThreshold`(기본 0.5m)일 때만 `AddWork` 누적.
  - 팔이 못 닿으면 대기(준비), 닿으면 체결값 증가, 차량이 멀어져 거리 벌어지면 증가 멈춤.
- 콜라이더 점유 차량 추적: `OnTriggerEnter` 등록 → 비면 `TryBeginAssembly`로 대상 선정, `OnTriggerExit` 시 진행중이면 포기·제자리 복귀 후 남은 차량 재시도.
- 주의(고친 버그): `AssemblyPart.Awake`가 `armLookTarget`을 `GetComponentInChildren<Transform>()`(자기 자신)으로 덮어쓰던 것 → 인스펙터 지정 존중 + 없으면 자식 "ArmLookTarget" 탐색으로 수정.
- 완성시간 = `requiredWork / assembleSpeed` (닿아 있는 동안 기준).
- 이전(체류시간 타워디펜스 모델)은 폐기: "부품이 팔에 닿지 않아도 알아서 체결되는" 문제 때문에 IK 도달 게이트로 회귀.

### 파츠별 난이도 `requiredWork` (10~100 / 평균 50)
- 옆면(문/바퀴 등): 크게(예 100) — 체류시간 길어 자연히 채워짐
- 앞면(범퍼 등): 작게(예 10) — 선두라 사거리 체류 짧아 빨리 끝나야 함
- 앞쪽 파츠 차체 관통 문제는 **로봇/콜라이더 배치**로 해결 (앞 부품=앞쪽 로봇)

### 체결 값 `currentWork` (방향: 0 → requiredWork, 증가)
- 기존 `assemblyProgress`(1→0) **폐기**.
- `0` = 분리(pile, 숨김), `requiredWork` = 체결완료.
- 위치 보간: **큐빅 베지어** `pile → mid2 → mid → assembled` (`Fill = currentWork/requiredWork`).
  - mid/mid2는 통과점이 아니라 **곡선 제어 핸들**.

## 3. 주요 스크립트 현황

## 5. 바퀴 리프트 공정 + 라인 정체(트래픽) 설계 (2026-07-12)

> 바퀴 4개는 흐르면서 체결하지 않는다. 전용 리프트 공정에 차량이 **정지** →
> 리프트가 차를 들어올림 → 로봇팔 동시 작업(고정 시간창) → 내려서 재출발.
> 시간창 안에 못 끝낸 바퀴는 **안 붙은 채 출고**(부분 체결 = 부드러운 실패).

### 5-1. 라인 정체 방식 = 어큐뮬레이션 (결정)

현재 CarController는 차간 인지 없이 각자 `pathProgress`를 증가시키는 개별 이동.
정지 차량이 생기면 뒷차 처리가 필요 — 후보 3안 비교:

| 방식 | 동작 | 판정 |
|---|---|---|
| ① 블록 신호식 | 정지구간 점유 시 상류 차량 전부 그 자리 정지 (7m 간격 유지한 채) | ✗ 라인 버퍼 낭비, 띄엄띄엄 멈춰 어색 |
| ② **어큐뮬레이션 (채택)** | 뒷차는 앞차 꽁무니 **minGap까지 접근 후 정지**. 줄서기 발생 | ✓ 실제 공장 컨베이어와 동일, 줄서는 시각 압박 = 업그레이드 동기 |
| ③ 추종 모델(IDM류) | 앞차 속도 매칭 감속 | ✗ 과설계. 1D 단일 라인엔 불필요 |

- **minGap = 5m** (차량 길이 4.5 + 여유 0.5, 호길이 기준). 스폰 피치 7m(속도×스폰주기)는
  흐를 때의 간격일 뿐 불변량 아님 — 정지구간 앞에서 5m로 압축되는 게 의도된 그림.
- **감속 밴드 decelBand = 2m**: gap 7m→5m 구간에서 속도 100%→0 선형 감속
  (`speedFactor = clamp01((gap − minGap) / decelBand)`). 하드 클램프의 급정거 방지.
  체결 소프트 게이트와 동일 패턴이라 튜닝 감각 공유.
- 리프트에서 방출된 뒤 하류 간격은 속도×리프트사이클로 재배열됨 — 자연스러운 현상, 방치.

### 5-2. LineTrafficManager (신규, MonoSingleton)

- **활성 차량 리스트를 pathProgress 내림차순 유지.** 스폰은 항상 라인 시작(꼬리)이고
  추월이 없으므로 정렬은 스폰 시 꼬리 삽입만으로 유지 (재정렬 불필요).
- 등록/해제: `CarController.SetPath`에서 Register, 출고/`CarPool.Return`에서 Unregister.
- **이동 주도권을 매니저로 이관**: 매 프레임 선두→후미 순서로 `car.MoveStep(maxProgress)` 호출.
  `maxProgress = 앞차.pathProgress − minGap/splineLength` (선두는 1f).
  선두부터 갱신하므로 같은 프레임 값 기준 클램프 = 1프레임 지연/스크립트 실행순서 이슈 없음.
- CarController는 **매니저 없으면 기존 자율 이동 폴백** (TestPartsScene 등 기존 씬 무변경).
- **스폰 가드**: `CarSpawner.SpawnCar` 시 시작점 앞 minGap 이내에 차가 있으면 스폰 보류
  (타이머 리셋 안 함 → 자리 나면 즉시 스폰). 큐가 스포너까지 차면 자연 스로틀 = 정체의 최종 비용.

### 5-3. WheelStation (리프트 공정, 신규)

상태기계: `Idle → Entering → Raising → Working → Lowering → Releasing → Idle`

- **위치**: `liftProgress`(스플라인 진행도 0~1)로 정의. Idle일 때 차가 `pathProgress ≥ liftProgress`
  도달하면 캡처: liftProgress로 스냅 + `isMoving = false`. 트래픽 관점에선 그냥 "멈춘 선두"라
  뒷차 줄서기는 5-2가 자동 처리 — 리프트는 뒷차를 전혀 몰라도 됨.
- **승강 연출**: `isMoving=false`면 SnapToProgress가 안 돌아 transform이 자유 →
  리프트가 차량 Y를 직접 DOTween 애니메이션 (기계 메시도 함께 상승). 내릴 때 원위치 복원.
- **로봇팔 4개 직접 오케스트레이션**: 트리거 진입 의존 X. Working 진입 시 WheelStation이
  각 StationController에 체결 시작 명령(동시 시작 연출 보장), **시간창 T 종료 시 미완료
  스테이션 강제 ResetStation**. 차량이 정지 상태라 dist≈0 → 기존 소프트 게이트가 전속 체결
  (게이트/AddWork 코드 재사용, 수정 불필요).
- **부분 체결**: T 안에 끝난 바퀴만 IsAssembled. 미체결 바퀴는 빠진 채 출고 = 시각적 재미 +
  판매가 감액 (현재 all-or-nothing 출고판정 → 부품 수 비례 감액으로 확장 필요).
- **초기 가동 팔 2개(앞바퀴)** → 업그레이드로 4개 해금.

### 5-4. 업그레이드 레버 / 파급효과

- 레버: ①리프트 승강 속도(사이클 오버헤드) ②시간창 T ③동시 가동 팔 수 2→4
  ④assembleSpeed 배율 ⑤(후반) 듀얼 리프트 = 병목 근본 해소 고가 목표.
- 처리량 = min(스폰율, 1/리프트사이클). 라인속도 업그레이드할수록 리프트가 병목으로
  부상 → 병목 옮겨가기 순환 완성.
- ⚠️ **이머전트 효과**: 정체로 멈춘 차가 일반 스테이션 작업존 안에 서 있으면 그 부품은
  전속 체결됨(정지 = dist≈0). "정체 = 처리량↓ 품질↑" 트레이드오프 — 일단 의도된 재미로
  수용, 밸런스 문제 시 재검토.
- 구현 순서 제안: ⑴ LineTrafficManager + CarController.MoveStep 분리 (리프트 없이도
  정체 동작 단독 검증 가능 — 차 하나 isMoving=false로 수동 정지시켜 테스트)
  ⑵ WheelStation 상태기계+승강 ⑶ 부분 체결 출고판정 확장 ⑷ 업그레이드 배선.

> 판정한다. WheelStation과 마찬가지로 `ILineGate` 구현 + `LineTrafficManager` 게이트 등록.

- **상태 머신 12단계**: `Idle → HangerDescending → Grabbing → Lifting → TravelToPool →
  Submerging → Testing → Emerging → TravelToLine → Lowering → Releasing → Cooldown`.
  행거 이동은 전 구간 `MoveHangerGrabTo()`(hangerRoot를 MoveTowards, grabPoint가 목표
  0.05m 이내 도달 시 완료) 하나로 통일.
- **판정**: `Testing` 진입 시 `CountUnassembledParts()`로 미체결 수 확인 →
  0=Pass / `majorDefectThreshold` 미만=MinorDefect(반액 보너스) / 이상=MajorDefect(보너스 없음).
- **결과 분기**:
  - Pass → `releasePoint`(게이트 이후 라인 위)에 내려놓고 `SetProgress(releaseProgress)` +
    `isMoving=true`로 라인 정상 복귀. `releaseProgress`는 `autoProgressFromPosition` 켜져
    있으면 releasePoint 위치에서 자동 계산.
  - Defect → `rejectPoint`(폐기 구멍)로 이송 후 `CarPool.Return()`으로 소멸. `TravelToLine`
    시작 시 즉시 `LeaveLine()` 호출해 뒷차가 게이트 클램프에서 풀리도록 하고, 동시에
    `rejectDoor`(슬라이딩 문)를 `TravelToLine`~`Lowering` 구간에서 미리 열어 도착 전에
    완전히 열리도록 함. `Cooldown`에서 문 원위치 복귀.
- **이펙트**: 입수/출수 스플래시, 검사 중 일반 기포(+불량 시 defect 기포 추가), 불량 감지
  스파크(failVFX, 물속에서), 통과 시 passVFX. 인스펙터 우클릭 "임시 VFX 생성" 컨텍스트
  메뉴로 파티클 5종 + URP 재질(`Assets/@Resource/Materials/VFX/VFX_*.mat`) 자동 생성
  (알파블렌드=물/기포, 가산합성=Pass/Fail).
- **씬 셋업**: `HangerRoot > HangerGrabPoint`, `PoolEntryPoint`, `PoolBottomPoint`,
  `ReleasePoint`(게이트 이후 스플라인 위), `RejectZone > RejectPoint + RejectDoor`.

저장/로드.

**핵심 메커니즘 설계 방향**:
- **사람 작업자**: 초기 공정 담당. 휴식시간에는 체결 진행 안 됨 → 차량이 앞으로
  이동 못함. 작업 재개 시 체결 진행.
- **작업자 불량/변수**: 사람 특성상 확률적 불량 발생 가능 (로봇팔과 대비되는 지점).
- **노조 파업 이벤트**: 전체 이벤트로 발생, 현재 수익의 일정 %를 지불해야 파업 해지.
  단발성 버튼이 아니라 지속시간에 따라 %가 늘어나거나 방치 시 라인 전체 정지 등
  긴장감을 주는 방식으로 밸런싱 필요 (아직 미확정, 구현 시 설계 필요).
- **자동화 전환**: 사장(유저)이 인력 관리 번거로움 때문에 로봇팔 업그레이드를
  선택하는 방향으로 유도.

**리스크 / 주의할 점**:
1. **전환 페이싱이 핵심** — 사람→로봇 전환이 너무 빠르면 사람 파트가 튜토리얼처럼
   스쳐가고 결국 로봇팔 단조로움이 후반부에 재현됨. 너무 느리면 관리 번거로움이
   짜증으로만 남음.
2. **"완전자동화 = 게임 끝" 서사의 이중적 의미** — 포트폴리오/2시간 환불 관점에선
   타당하지만, 상업적 장기 출시까지 염두에 둔다면 완전자동화 이후 후속 확장 여지
   (멀티 팩토리, 수출 계약 등)를 구조적으로 열어둘 필요.
3. **사람 캐릭터 애니메이션 비용** — 걷기→작업 전환→작업 자세 블렌딩은 로봇팔보다
   리깅/애니메이션 비용이 더 큼. 풀 휴머노이드보다 단순화된 표현(예: 상반신 위주
   애니메이션, 로우폴리 스타일) 고려 권장.
4. **파업 이벤트 밸런싱** — 단발성이면 긴장감 없이 세금 알림처럼 소비될 위험.

**아키텍처 메모**: 기존 `ILineGate` 인터페이스(`WheelStation`, `WaterTestStation`이
구현)에 `WorkerStation` 구현체를 추가하는 방식. 사람 작업자 스테이션 작업 시작 전

## 9. 인력·물류 관리 시스템 설계 (2026-08-18, 미착수 — 설계 논의 확정분)

> 8장 방향 전환(사람 작업자 → 로봇팔 자동화)의 구체화. 재미의 축을 "체결 애니메이션 관찰"에서
> **"인력·물류 관리 의사결정"** 으로 이동시킨다. 자동차 공장처럼 보이지만 실제로는 사람 관리 게임.

### 9-0. 선행 결정 (8장 방향 전환의 수정·보강)

- **작업자는 공정에 고정 배치한다.** 초기 구상이던 "작업자 1명이 차량을 따라 1공정→2공정→…→완성"은
  **기각**. 이유: ①컨베이어 라인·트래픽·게이트 공정이 전부 무의미해짐(셀 생산이 됨) ②작업자 추가가
  단순 병렬 증가라 선형 성장 = 의사결정 부재 → "로봇팔 배치일 뿐"이라던 기존 문제가 축만 바꿔 재현됨.
  고정 배치하면 공정별 `requiredWork` 차이에서 **병목**이 발생하고, "어느 공정에 인력을 더 붙일지 /
  라인 속도를 낮출지 / 그 공정만 먼저 로봇팔로 바꿀지"가 핵심 의사결정이 된다. (= 1장 원래 기획 유지)
- **"사람이 움직이는 볼거리"는 물류로 확보한다** — 아래 9-1. 작업자가 부품 파일↔차량을 왕복하고,
  보급 작업자가 창고↔공정을 왕복한다. 베지어 경로는 로봇팔에서 검증됐으므로 재사용.
- **체결 여부와 품질을 분리한다.** 현재 `currentWork ≥ requiredWork`(all-or-nothing)에 **품질값**을 추가.
  사람이 서둘러 붙이면 체결 100%지만 품질 60% → 방수/압력 테스트에서 확률적 실패. 로봇팔은 품질 고정 100%.
  → "사람 시대엔 검사 공정이 안전망으로 필수, 자동화할수록 통과율이 올라 검사를 줄일 수 있음"이라는
  자동화 보상 체감이 성립. 기존 우려("100% 체결되면 테스트 공정이 무의미해지나?")는 이 분리로 해소되며,
  이월 TODO였던 **부분 체결 감액 출고판정**도 같은 품질 축에 얹힌다.
- **성장 축은 3개 이상으로 분리** — 처리량(라인속도/작업자수/배치) · 품질(교육/로봇전환/검사) ·
  제품(차종 추가: 경차→세단→SUV→스포츠카, 단가·부품수·난이도↑). 여기에 9장의 **인력·물류**가 4번째 축.
  차종 추가는 파츠 조합·requiredWork만 바꾸면 되므로 리텐션 대비 비용이 가장 싸다.

### 9-1. 공정 부품 재고 + 물류 (★ 핵심 신규 재미 축)

- **각 공정에 부품이 실제로 쌓여 있다.** 파일(pile)에 물리적으로 적재된 부품이 체결마다 **눈에 보이게 줄어든다.**
  (기존 `stationPilePos` + `stationPileMesh`를 스택 표현으로 확장)
- **재고 0 = 해당 공정 체결 불가 → 라인 정지.** 라인 정지가 곧 손실이므로 유저에게 즉각적 압박이 된다.
- **보충 수단 3단계 (자동화 테마의 축소판):**
  1. **유저 직접 클릭** — 응급조치. 반드시 **비효율적이어야 한다**(1회 소량 + 쿨타임, 또는 창고→공정
     왕복 필요). 클릭이 너무 효율적이면 보급 작업자를 아무도 고용하지 않고, 너무 무력하면 짜증만 남는다.
  2. **공정 작업자가 직접 창고에 다녀온다** — 그 동안 해당 공정 체결 중단(기회비용). 초반 기본 동작.
  3. **전담 보급 작업자 고용** — 창고↔공정 순회 보충. 공정 작업자는 체결에만 집중.
- **보급 작업자 수는 상한이 있다**(무한 증원 불가) → 인원을 늘리는 게 아니라 **업그레이드**로 해결하게 유도.
  - 업그레이드 경로: 맨손 운반 → 손수레 → **지게차**(더 빠르고 1회 적재량↑).
  - ⚠️ 지게차는 통로/경로 개념이 필요해짐(NavMesh 또는 통로 웨이포인트) → **라인 레이아웃 설계가
    또 하나의 의사결정 레이어**가 되는 이득이 있으나 구현 비용도 커짐. 후순위 단계로 배치.
- 설계 효과: 물류는 체결 속도와 **직교하는 두 번째 병목**이다. 라인 속도를 올리면 체결 누락뿐 아니라
  부품 소모 속도도 올라가 물류가 먼저 터진다 → 단일 축 성장의 답답함이 구조적으로 해소된다.

### 9-2. 작업자 상태 세분화 + 머리 위 상태 표시

- 상태를 세분화하고 작업자 옆/위에 아이콘으로 표시한다. 방치형·관리형에서 **"한눈에 병목 파악"** 이 핵심 UX.
- 상태 예: `출근중 / 이동중 / 작업중 / 부품가져오는중 / 부품없음(대기) / 휴식중 / 피로 / 불량발생`.
- **표시 원칙: 정상 상태는 아이콘을 띄우지 않는다.** 문제 상황(부품없음·휴식·피로·불량)만 뜨게 해서
  화면 노이즈를 줄이고, 아이콘이 보이는 곳 = 유저가 개입할 곳이 되도록. 종류는 5~7개로 제한.

### 9-3. 경제: 고정비(급여) 도입

- **돈이 벌리기만 하지 않고 빠져나간다** — 작업자 급여 = 고정비. 순증 경제는 긴장이 없다.
  고정비가 있으면 **"고용 = 리스크"** 가 되고 손익분기 판단이 생겨 비로소 타이쿤이 된다.
- **급여일에 한 번에 빠지게 한다**(주급 등) → 급여일 전 처리량을 밀어붙이는 **긴장의 리듬**이 생긴다.
  매 프레임 조금씩 빠지면 체감이 없다.
- **★ 이 축이 로봇팔의 존재 이유를 완성한다**: 로봇팔 = 초기 비용 크지만 **급여 0**(소액 정비비만).
  그동안 애매했던 "로봇팔이 왜 좋은가"에 경제적 답이 생기고, 엔딩(전 라인 로봇팔화)이 곧 **"인건비 0"**
  이라는 서사적 의미까지 갖는다.
- **파산은 게임오버로 만들지 않는다** — 방치형에서 하드 실패는 짜증이 크다. 대출/평판 하락/납기 지연
  같은 소프트 페널티로 처리.

### 9-4. 시간 흐름 + 근무·피로·휴식

- **하루 시간 표시 + 출근 연출**: 07:00 작업 시작이면 06:30경 작업자들이 입구에서 각자 자리로 이동.
  저비용 고효과. 하루의 시작 신호가 되어 게임에 리듬을 만든다.
- 실시간이면 지루하므로 **시간 압축 배율** 필요(예: 1일 = 실시간 10~20분). 배속/스킵은 무료 기본 기능.
- **8시간 근무 중 1시간 휴식(최소 10분 ~ 최대 1시간)** — 휴식 중엔 해당 공정 체결 중단 → 라인 압박.
  - ⚠️ **완전 랜덤은 지양.** 대응 수단이 없는 랜덤은 불공평·짜증으로 읽힌다. **피로도가 임계치에 도달하면
    휴식**(예측 가능한 인과)으로 두고 랜덤 폭은 작게. 그러면 유저가 휴게실 업그레이드·교대 배치·예비
    인력으로 **대응할 수 있게** 되어 의사결정이 된다.
  - 휴식으로 멈춘 공정은 유저 직접 개입(위기 개입) 또는 유휴 작업자 재배치로 메꿀 수 있게 한다.
  - 공정 1개 정지가 전 라인 정지로 이어지면 페널티가 과도하므로, 공정 간 **버퍼 재고**로 완화 설계 필요.

### 9-5. 야간 정비 시간 (프레임 수정: 처벌 → 보상)

- **원안**: 07:00~24:00 2교대, 24:00~07:00은 유저가 부품 보충·더러운 작업대 청소. 청소 안 하면 작업효율
  −20% + 피로 20% 가속 디버프. 앱 결제로 시간 점프 및 자동 청소.
- **⚠️ 이 부분만 방향을 뒤집을 것을 권고 (미확정, 재논의 대상):**
  1. **"안 하면 디버프"는 처벌 기반 반복 노동(chore)** 이다. 매일 반복되는 청소는 게임이 아니라 숙제가 되고,
     그걸 결제로 지우는 구조는 **pay-to-remove-annoyance** — 리뷰 폭격의 대표 원인.
  2. **플랫폼 불일치**: 스팀 유저는 소액결제로 불편을 제거하는 설계에 매우 적대적이다(모바일 F2P 문법).
     스팀 목표라면 buy-to-play / DLC가 맞다. 포트폴리오 관점에서도 IAP 구현은 채용 가점이 거의 없고
     오히려 게임 이해도를 의심받을 수 있다.
- **수정안**: 야간 정비 시간이라는 아이디어 자체는 살리고 프레임만 뒤집는다.
  - 청소 **안 함 = 기본 상태(디버프 없음)** / 청소 **함 = 버프**(작업효율 +10%, 다음날 피로 축적 감소).
    같은 인센티브가 처벌이 아니라 보상으로 작동한다.
  - 자동화는 **결제가 아니라 게임 내 성장으로** 풀게 한다: **사장이 직접 청소 → 청소 작업자 고용 →
    자동 청소 로봇 구매.** 이 3단계는 게임 전체 테마(사람→자동화)의 축소판이라 주제와 완벽히 일치한다.
  - 시간 점프/배속은 무료 기본 기능으로 제공.
- **청소 작업자**는 이 설계에서 정식 직군으로 편입(공정 작업자 / 보급 작업자 / 청소 작업자).

### 9-6. 구현 우선순위 (스코프 관리)

9장 전체를 한 번에 넣으면 스코프가 터진다. 아래 순서로 단계별 검증 권장.

1. **핵심 루프** — `ILineGate` 구현체 `WorkerStation`(공정 고정 배치) + 공정 부품 재고/파일 감소 +
   재고 0 시 라인 정지 + 유저 클릭 응급 보충 + 상태 표시 아이콘(최소 `부품없음`). **품질 필드만 미리 심어둠.**
2. **물류 1단계** — 공정 작업자의 창고 왕복 → 전담 보급 작업자 고용 + 인원 상한.
3. **경제** — 급여 고정비 + 급여일 리듬 + 손익분기 UI.
4. **인적 변수** — 피로도/휴식(임계치 기반) + 상태 세분화 완성 + 확률적 불량 → 품질 축 활성화(검사 공정 연동).
5. **시간** — 하루 시간 흐름 + 출근 연출 + 시간 압축 배율.
6. **야간 정비** — 보상형 청소 + 청소 작업자 → 자동 청소 로봇.
7. **자동화 전환 경제** — 로봇팔 = 고초기비용/무급여로 재배치, 공정별 전환, 전 라인 전환 = 엔딩.
8. **물류 2단계(후순위)** — 손수레 → 지게차 + 통로/경로탐색 + 라인 레이아웃 의사결정.
9. **파업 이벤트**(8장 항목) — 급여·피로·청소 상태와 연동시켜 인력 관리의 최종 리스크로 배치.

> **작업 우선순위 메모**: 사운드/이펙트 등 폴리시는 유저 판단으로 **후순위**. 시스템 구축이 우선.
> (단 8장 진단에서 지적한 "피드백 빈약" 문제는 시스템 완성 후 반드시 회수할 것 — 체감 개선폭이 크다.)

### 9-7. 세부 확정 (2026-08-18 후속 논의)

**⑴ 유저 클릭 보충 (확정)**
- 클릭 1회 = 재고 **3개** 적립. 이후 **쿨타임** 동안 다른 공정도 추가 보충 불가(전역 쿨타임).
- **쿨타임 즉시 초기화 수단**: 카메라를 **창고 위치로 이동**해서 창고를 클릭. → 시간이 아니라
  **주의력·화면 기회비용**을 대가로 지불하는 구조(창고를 보는 동안 라인을 못 본다). 단순 쿨타임보다 좋음.
- **보급(재고관리) 작업자는 기본 1명 지급**으로 시작(당초 "0명 시작" 수정). 유저 클릭은 처음부터
  **응급 수단**으로 자리 잡고, 성장은 "보급 인원 상한 내 증원 → 손수레 → 지게차" 업그레이드로 진행.

**⑵ 로봇팔의 우위 = 고정비 0 + 가동률 100% (확정)**
- 급여 0(정비비만)이라는 **비용 우위**에 더해, **휴식이 없어 가동률이 100%** 라는 **처리량 우위**가 함께 있음.
  사람은 컨디션 소모로 필연적 휴식 → 로봇팔 전환의 동기가 비용·처리량 두 축에서 성립.

**⑶ 자금 마이너스 페널티 (⚠️ 중첩 주의 — 확정 필요)**
- 후보: ①작업자 이동속도 반감 ②판매액 20% 감소 ③업그레이드 등 재화 사용 잠금 + 벌리는 재화로 점차 상환.
- **권고: ③을 기본으로 하고 ①②는 넣지 않거나 매우 약하게.** 이유 = ①②는 **처리량 자체를 깎아서
  상환을 불가능하게 만드는 죽음의 소용돌이(death spiral)** 를 유발함. 마이너스에 빠진 유저가 더 못 벌게
  되면 회복 경로가 사라져 방치형에서 가장 나쁜 체감이 된다.
- ③만으로도 **성장 정지**라는 충분히 아픈 페널티이며, 처리량은 유지되므로 **회복 가능**하다.
  긴장을 더 주고 싶으면 ①②를 넣되 **마이너스 지속 일수에 비례해 단계적으로**(1일차 없음 → 3일차 10% →
  5일차 20%) 적용해 즉사 방지.

**⑷ 작업자 상태 표시 (확정·간소화)**
- 상태 = **부품없음 / 휴식중 / 작업중** + **컨디션 게이지**(아래 ⑸). **불량 아이콘은 제거**.
  `피로` 아이콘도 컨디션 게이지와 중복이므로 **게이지 색 변화로 대체**.
- **`작업중` 상태에서 유저가 클릭하면 체결량(work)을 추가 적립** — 상시 참여형 개입.
  - 밸런싱: 클릭당 고정량으로 두면, 공정 수가 늘어날수록 **물리적으로 다 못 누르게 되어 자연스러운 상한**이
    생긴다(별도 제한 장치 불필요). 규모가 커질수록 클릭의 상대적 영향력이 줄어 **자동화 유도**로 이어짐.
- **품질 축은 내부 값으로 유지**(아이콘만 제거): 컨디션이 낮을 때 체결하면 품질 하락 → 검사 공정 연동.

**⑸ 컨디션 게이지 (확정 — 랜덤 휴식 대체)**
- 작업자마다 **컨디션 100% 시작**. **차량 1대 담당 완료마다 −10%** → 게이지 + 색 변화로 표시.
  0% 도달 시 **강제 휴식**. → 9-4의 "8시간 중 랜덤 1시간 휴식"은 **폐기**, 완전 예측 가능한 인과로 대체.
- **선제 관리**: 체결을 마치고 **다음 차량을 기다리는 유휴 시간**에 유저가 클릭하면 미리 휴식 → 라인 정지 예방.
- **핵심 밸런싱 레버 = 선제 휴식과 강제 휴식의 비대칭**: 선제 휴식은 짧게/회복 효율 높게, 강제 휴식은
  길게 두어야 "미리 관리하는 플레이"에 보상이 생긴다. (동일하면 관리할 이유가 없어짐)
- 유저는 "10대 = 1사이클"로 카운트 가능 → 리듬이 읽히고 계획이 가능해짐.

**⑹ 야간 정비 (확정 — 스코프 축소)**
- **페널티 없음**(9-5 권고 수용). **작업대 더러워짐/청소 메커니즘은 이번 범위에서 구현하지 않음**
  (시간 대비 중요도 낮음). 청소 작업자·자동 청소 로봇도 함께 보류.
- **구현 범위는 "다음날로 스킵" 버튼만.** 스킵 시 **다음날 06:30**(출근 시각)으로 이동.
- 청소/버프 재도입 여부는 시스템이 자리 잡은 뒤 재논의.

### 9-8. 최종 확정 (2026-08-18) — 9-7 ⑶⑸ 결론

**⑶ 자금 마이너스 페널티 = 업그레이드 잠금만 (확정)**
- 마이너스 상태에서는 **재화 사용(업그레이드/고용/구매) 전면 잠금** + 벌리는 재화로 **점차 자동 상환**.
- **이동속도 반감·판매액 감소는 채택하지 않음** — 처리량을 깎으면 상환 능력까지 깎여 죽음의 소용돌이가 됨.
  성장 정지만으로 충분히 아프고, 처리량이 유지되므로 회복 경로가 남는다.

**⑸ 휴식 비대칭 (확정)**
- **선제 휴식 3초 / 강제 휴식 5초.** 회복량은 **양쪽 모두 컨디션 100% 전량 회복**(차이는 시간·타이밍만).
- **선제 휴식 조건**: 컨디션이 100% 미만이면 **유휴 상태에서 언제든** 클릭 가능(90%든 20%든).
  유저가 안전 마진을 스스로 정하는 것이 관리 재미의 핵심이므로 하한 제한을 두지 않는다.
- **비대칭의 실질은 길이가 아니라 타이밍**: 선제는 유휴 시간(다음 차량 대기)에 소화 → **기회비용 0**,
  강제는 작업 중 발동 → **라인 정지**. 2초 차이 자체가 아니라 "멈추는가"가 인센티브다.
- **파생 긴장(의도된 것)**: 라인 속도를 올리면 유휴 시간이 사라져 선제 휴식 창이 소멸 → 강제 휴식 리스크 상승.
  작업자가 늘면 클릭 대상이 늘어 주의력이 부족해짐 → 자동화 압박으로 연결.
- **⚠️ 튜닝 메모**: 차량 10대 작업이 ~60초라면 강제 5초는 다운타임 8%로 체감이 미미할 수 있음.
  긴장이 부족하면 **강제 쪽을 늘릴 것**(선제 3초 : 강제 10~15초). 절대값보다 **비율**이 레버.
- 구현 기준: 휴식 시간은 게임 시간(`Time.timeScale` 영향) 기준으로 두어 배속·스킵과 일관되게 처리.

- 공장 내부에 **광고판**을 설치해 **3초마다 순환 표시**: 결제(후원)한 유저 아이디, 또는 개발자에게 보내온

- **승인 구조가 중요**: "보내주면 내가 보여준다" = **수동 큐레이션**이므로 안전하다. 유저 생성 콘텐츠를
  자동으로 게임에 띄우면 욕설·혐오·저작권 이미지가 그대로 노출돼 스팀에서 치명적 문제가 되는데,
  이 방식은 그 리스크가 원천 차단된다. **자동 반영 파이프라인은 만들지 말 것.**
- **구현 경량화**: 결제 시스템·서버 연동 없이 **원격 JSON(또는 내장 텍스트 목록) 한 장을 읽어 순환**하는
  방식으로 충분. 게임 업데이트 없이 목록만 갱신 가능. **텍스트 우선**(이미지는 용량·저작권·해상도 부담).
- 배치: 공장 벽면/천장 현수막. 3D TMP + 3초 간격 페이드 전환(CashPopup의 DOTween 패턴 재사용 가능).
- **우선순위: 9-6의 중반부(5~6단계 사이)에 삽입.** 핵심 루프·물류·경제가 검증된 뒤 착수.

### 9-11. 정지형/흐름형 확정과 로봇팔 체결률 (2026-08-18 문답 정리)

**Q1. 사람 공정은 무조건 정지형인가? → 그렇다.**
- 재고 0 → 라인 정지가 **게이트를 활성 유지하는 것만으로 성립**한다(기존 `LineTrafficManager` 인프라 재사용).
  흐름형이면 라인 정지를 트래픽과 별도로 새로 구현해야 한다. 기획적으로도 사람이 서서 작업하는 게 맞다.
- **파이프라이닝은 유지된다**: 게이트가 여러 개면 각 게이트마다 차량 1대가 동시에 작업받으므로 병렬성이 있고,
  **라인 처리량은 가장 느린 공정(병목)이 결정한다.** → 9-0에서 노린 "병목이 재미의 원천"과 정확히 일치.
- **★ 부수 이득(설계 의도 외)**: 사람=정지형 / 로봇팔=흐름형이면 **자동화 보상이 눈에 보인다.**
  사람 시대의 라인은 stop-and-go로 덜컹거리고, 로봇팔로 바꾼 공정부터 차량이 멈추지 않고 흐른다.
  전 라인 로봇팔화(엔딩) = **라인이 완전히 매끄럽게 흐르는 순간** → 엔딩 연출로 쓸 수 있을 만큼 강한 카타르시스.
  "급여 0 + 가동률 100%"라는 수치 우위가 시각적 언어로 번역된다.

**Q2. 로봇팔은 무조건 체결 100%가 되어야 하나? → 혼재 상태에서는 자연히 100%가 된다.**
- 사람 공정(정지형)이 라인을 계속 멈추므로 로봇팔 공정에는 항상 시간 여유가 생긴다 → 누락이 발생하지 않음.
  **이는 결함이 아니라 자동화의 보상**이다("로봇팔로 바꾼 공정은 더 이상 신경 쓸 필요가 없다").
- **단, 전 라인 로봇팔화(엔딩) 이후에는 멈추는 공정이 사라져 라인 속도 vs 체결 속도 경쟁이 부활**한다
  → 누락 가능성이 다시 생긴다. 이것을 **엔딩 이후의 밸런싱 레버**로 쓴다:
  라인 속도 업그레이드로 처리량을 올리면 누락 리스크가 따라온다 = **유저가 스스로 켜는 리스크**(이상적 구조).
- 검사 공정(방수/압력/속도)의 존재 이유는 **사람이 붙인 부품의 품질값**이 담당한다(9-0 체결/품질 분리).
  로봇팔 체결이 100%여도 검사가 무의미해지지 않는다.

### 9-12. 1단계 구현 1차분 (2026-08-18, 미컴파일검증)

**코드 실측 결과 (설계 전제 확인)**
- `ILineGate`는 멤버 2개(`GateProgress`/`GateEnabled`)뿐이고, 감속 도킹·뒷차 줄서기·통과 판정은

  → **결정 A = 정지형 게이트** 확정. 재고 0 → 라인 정지가 게이트 유지만으로 성립.
- `StationController`는 로봇팔 강결합(`Update` 첫 줄 `if (robotArm == null) return;`, 체결 동력이 IK 거리
  소프트 게이트) → **건드리지 않는다.** 사람 공정은 `AssemblyPart` 공개 API를 직접 구동한다.
- `PartResourceManager`는 재고가 아니라 **부품 프리팹 경로 매핑** → 재고 스택 시각화에 재사용.

**신규/수정 파일**
- **신규 `PartStack.cs`**(Comm/Object): 공정 재고. 부품 프리팹을 capacity개 미리 생성해 `SetActive`로
  개수만 토글(생성/파괴 없음 = GC 0, CarPool·코인 풀링과 동일 원칙). 표시용 인스턴스는 `AssemblyPart`를
  `enabled=false`로 꺼서 체결 로직이 집어가지 않게 한다. API: `TryConsume/Add/Fill_Full/SetPartType`,
  `Count/Capacity/IsEmpty/IsFull/Fill`. 슬롯 위치 기즈모 + 재고 라벨.
- **신규 `Worker.cs`**(Comm/Object): 사람 작업자. 상태 = `GoingToWork/Idle/Fetching/MovingToPart/
  Working/Resting/OffWork`. 체결은 `BeginWorldAssembly → AddWork → SetAssembled`만 사용(로봇팔 무관).
  - **체결 게이트 = "작업자가 부착점 옆에 도착했는가"** (로봇팔의 IK 거리 게이트에 대응).
  - **부품을 손에 들고 간다**: `MovingToPart` 동안 매 프레임 `BeginWorldAssembly(손 위치)`로 pile 기준점을
    갱신 → fill=0인 부품이 손에 붙어 따라온다. 작업 위치 도착 시 갱신을 멈추면 '손 → 부착점' 이동이 된다.
    (`BeginWorldAssembly`가 순수 setter라 진행도에 영향 없음을 확인하고 채택)
  - 컨디션 100% → 차량 1대 완료마다 −10% → 0이면 강제 휴식 5초 / 유저 클릭 선제 휴식 3초, 양쪽 전량 회복.
  - **품질**: 완료 시 `part.quality = Lerp(qualityAtZeroCondition, 1, 컨디션비율)` — 지친 작업자가 붙이면
    체결 100%여도 품질이 낮다.
- **신규 `WorkerStation.cs`**(Comm/Object, `ILineGate`): 정지형 공정. `Idle`(게이트 대기) → 캡처 →
  `Working` → 담당 부품 전부 완료 시 `PassGate` 방출. 담당 부품 배열 + 재고 파일 배열 + 작업자 배열
  (작업자를 늘리면 담당 부품을 병렬 처리). 파츠 완료마다 `partReward` 지급(로봇팔 공정과 동일 지점).
  - ⚠️ **성능 주의사항 반영**: `CarController.GetUnassembledPart`는 **호출마다 `Debug.Log`를 남긴다.**
    매 프레임 호출하면 로그 폭주 + GC → **캡처 시점에 1회만 조회해 `pending` 목록으로 캐시**하고
    이후 프레임은 캐시만 본다. (WheelStation은 캡처 때만 호출해서 문제가 없었음)
  - 재고 소모는 배정 시점 1개. 배정 실패·사이클 중단 시 `stockTaken` 플래그로 되돌려 재고 유실 방지.
  - `IsBlockedByStock()` = 재고 부족으로 라인이 멈춴 상태인지(표시용).
- **`AssemblyPart.cs`**: `quality`(0~1, 기본 1) 필드 추가 + `Reset()`에서 1로 초기화(풀 재사용 대비).

- **`InputManager.cs`**(스텁 → 구현): 클릭 라우팅. 파일 클릭 = 재고 +3 + 전역 쿨타임(기본 8초),

  - 메모: **레이어 충돌 매트릭스 제약은 트리거 감지에만 적용**되고 `Physics.Raycast`는 무관하므로

### 9-13. 1단계 상태 표시 UI + 씬 셋업 가이드 (2026-08-18)

**신규 `WorkerStatusUI.cs`**(Comm/Object, `[RequireComponent(typeof(Worker))]`)

**씬 셋업 순서 (Car_Factory 3 또는 테스트 씬)**
1. **작업자 프리팹/오브젝트**: 빈 GameObject(또는 캐릭터 모델) + `Worker` + `WorkerStatusUI`

     (미설정 시 몸 앞쪽 위로 자동 계산 — `handForward`/`handHeight`).
   - 작업자를 놓아둔 위치가 곧 **자기 자리(home)** 가 된다(WorkerStation이 Start에서 기록).
2. **부품 파일**: 빈 GameObject + `PartStack` + **클릭용 Collider**(응급 보충 클릭 대상).
   `partType` 지정(또는 WorkerStation이 자동 지정), `capacity`(기본 12), `stepOffset`/`perRow`/`rowOffset`으로
   쌓이는 모양 조정 — 씬 기즈모에 슬롯 위치와 `재고 n/N` 라벨이 표시된다.
3. **공정**: 빈 GameObject + `WorkerStation`을 라인 옆(차량을 세울 지점 근처)에 배치.
   - `targetPartTypes`에 이 공정이 담당할 부품들, `partStacks`에 대응 재고 파일, `workers`에 작업자들.
   - `pilePos`에 부품이 등장할 위치(보통 PartStack 위치) 지정 — 미설정 시 자기 위치.
   - `autoProgressFromPosition`이 켜져 있으면 **오브젝트를 옮기는 것만으로 게이트 지점이 따라온다**
     (플레이 중에도 Idle이면 갱신 — 위치 튜닝이 쉽다). 기즈모에 게이트 지점 구 + 라벨 표시.
4. **InputManager**: 씬에 하나 배치(없으면 클릭 개입이 동작하지 않는다).

5. **주의**: 같은 부품을 담당하는 로봇팔 `StationController`가 근처에 있으면 둘이 같은 파츠를 두고 경쟁한다.
   사람 공정으로 돌릴 구간의 로봇팔 스테이션은 **비활성화**할 것(추후 자동화 전환 시 반대로 전환).

**검증 시 볼 것**

### 9-14. 성장 축 전환 — "인원 추가"에서 "작업자 업그레이드"로 (2026-08-19, 미구현 — 설계 결정만 확정)

**배경 — 1단계 구현 후 발견된 코드상 성질**

`WorkerStation.TryAssignWork`가 `workers` 배열을 **인덱스 순으로 훑어 가용한 첫 작업자에게 배정**한다.
따라서 한 공정에 작업자가 2명 이상이면 0번이 컨디션 0으로 쉬는 동안 1번이 그대로 이어받는다.
결과적으로 9-7 ⑸에서 핵심 밸런싱 레버로 잡았던 **"피로로 라인이 멈춘다"는 압박이 1인 공정에서만 성립**하고,
인원을 늘리는 순간 사실상 무력화된다. 즉 인원 추가는 "관리 의사결정"이 아니라 **압박 제거 버튼**이 된다.

이 성질을 유저에게 확인했고, 아래 답변으로 성장 축을 전환하기로 확정했다.

> "한명을 추가해서 작업을 동시 작업해서 속도를 높이고 피로도를 낮춘다 라고 생각을 했는데, 그럴 필요 없이
> 작업자를 업그레이드 할 수 있는 시스템으로 가서, 작업자를 업그레이드하면 체결률을 높이거나, 피로도가 덜
> 감소하는 등 이런식으로 시스템을 관리하면 될 거 같고, 추가적으로 하나의 작업자가 아니라 전체 작업자에게도
> 패시브버프 느낌으로 이동속도 1퍼 증가 이런 업그레이드 시스템도 있어서 컨텐츠가 더욱 풍부하게 하면 좋을거 같아."

**결정**: 공정 작업자의 성장 축은 **인원 추가가 아니라 업그레이드**다. 인원 추가는 성장 수단에서 내리고
(완전 금지는 아니되 기본 성장 경로로 삼지 않음), 대신 아래 두 계층의 업그레이드로 대체한다.
9-0의 "공정 고정 배치" 결정과도 일관된다 — 인원 병렬 증가는 그때도 "선형 성장 = 의사결정 부재"로 기각됐다.

**두 계층**

| 계층 | 적용 범위 | 게임 진행에서의 역할 |
| --- | --- | --- |
| **개별 작업자 업그레이드** | 그 작업자 1명에게만 | **병목 공정에 집중 투자**. `requiredWork` 차이로 생긴 병목을 어느 공정부터 풀지 고르게 만든다 = 라인을 읽는 의사결정 |
| **전역 패시브 업그레이드** | 모든 작업자에게 누적 | **완만한 전체 상승**. 개별 투자로 못 메우는 바닥을 천천히 올려 방치형 특유의 "계속 좋아진다"는 체감을 담당 |

- 둘은 대체재가 아니라 **역할 분담**이다. 개별은 뾰족하고 비싸게(즉시 체감), 전역은 무디고 싸게(누적 체감).
- 전역은 유저 답변대로 **1%씩 여러 단계** 같은 잘게 쪼갠 스텝이 어울린다 — 재화 사용처가 항상 열려 있어야
  "쓸 데가 없어 돈이 쌓이는" 방치형의 실패 패턴을 막는다.

**업그레이드 대상 후보 (`Worker.cs` 실제 필드 · 현재 기본값 기준)**

| 필드 | 현재 기본값 | 올리면(내리면) 게임플레이가 어떻게 바뀌는가 |
| --- | --- | --- |
| `assembleSpeed` | `4f` (work/초) | 유저가 말한 "체결률". 공정 통과 시간이 줄어 **처리량 직결** — 병목 공정 해소의 1순위 레버 |
| `moveSpeed` | `2.5f` (m/초) | 파일↔부착점 왕복이 빨라진다. 전역 패시브(+1%)의 예시로 유저가 직접 지목한 값 |
| `conditionCostPerCar` | `10f` | **내리는** 업그레이드. 10대 = 1휴식 리듬이 12대·15대로 늘어 라인 정지 빈도가 줄어든다 |
| `preemptiveRestDuration` | `3f` (초) | 선제 휴식이 짧아진다 = 미리 관리하는 플레이의 보상 강화 (9-7 ⑸ 비대칭 유지) |
| `forcedRestDuration` | `5f` (초) | 강제 휴식이 짧아진다 = 실수의 대가 완화. **선제와의 비대칭이 무너지지 않게 신중히** — 이 값을 3f 이하로 내리면 선제 휴식을 할 이유가 사라진다 |
| `qualityAtZeroCondition` | `0.5f` (0~1) | 지쳤을 때 붙인 부품의 최저 품질이 올라간다 = 검사 공정(방수/압력/속도) 불량률 하락. **품질 축 투자** |
| `workStandDistance` | `0.9f` (m) | 작업 위치가 부착점에 가까워져 이동 시간이 미세하게 준다. 다만 `handForward`(0.6)와의 간격이 좁아지면 도착 판정이 불안정해지므로(`GetAttachWorldPos` 주석의 진동 버그 참조) **업그레이드 대상으로 부적합** |
| `arriveRadius` | `0.25f` (m) | 도착 판정 반경. 게임플레이 의미가 없고 위와 같은 이유로 위험 → **대상 제외** |

→ 실질 후보는 **`assembleSpeed` / `moveSpeed` / `conditionCostPerCar` / `preemptiveRestDuration` /
`forcedRestDuration` / `qualityAtZeroCondition` 6개**. 처리량(2) · 지속력(3) · 품질(1)로 갈라져 있어
9-0의 "성장 축 3개 분리"와 그대로 맞물린다.

**구현 시 고려사항 (설계 메모 — 아직 미구현, 구현 방식은 추후 확정)**

⑴ **기본값 보존 + 유효값 계산이 필요하다.** 위 값들은 전부 인스펙터 직렬화 `public` 필드라
런타임에 배율 버프를 필드에 직접 곱하면 **원본이 파괴되어 되돌릴 수 없고**, 버프가 중복 적용되면
복리로 폭주한다. 접근 후보는 다음 3가지 — 장단이 갈리므로 구현 전에 유저와 확정할 것.

- **A. 프로퍼티 분리** — 직렬화 필드는 `baseAssembleSpeed`로 두고, 실사용은 읽기 전용 프로퍼티
  `AssembleSpeed => baseAssembleSpeed * indivMul * globalMul`로 계산. 원본 보존이 확실하고 버프 합성이
  한 곳에 모인다. 대신 **기존 코드의 참조 지점과 인스펙터 값이 전부 개명**되고, 씬에 배치된 작업자의
  직렬화 값이 초기화될 수 있다(개명 시 `[FormerlySerializedAs]` 필요).
- **B. 배율 필드만 추가** — 필드명은 그대로 두고 `assembleSpeedMul` 같은 배율을 곁에 두어 사용처에서
  곱한다. 변경이 가장 작고 기존 씬이 안전하지만, **곱하는 걸 빠뜨린 사용처가 생기면 조용히 버그**가 된다.
- **C. Start 스냅샷** — `Start`에서 인스펙터 값을 `_base*`로 복사해 두고, 업그레이드가 바뀔 때마다
  `현재값 = _base * 배율`로 **필드를 다시 써넣는다**. 사용처 코드를 하나도 안 고쳐도 되는 게 최대 장점.
  대신 인스펙터에 보이는 값이 런타임에 계속 덮여 **디버깅 시 원본을 눈으로 확인할 수 없다**.

> **확정 (2026-08-20): B(배율 필드) 채택.** 인스펙터 직렬화 기본값은 그대로 두고, 런타임 유효값만
> `기본값 × 배율`로 산출한다. 근거 — ⑴ 씬에 이미 직렬화된 작업자 값을 하나도 건드리지 않는다(A의
> 개명 리스크·`[FormerlySerializedAs]` 부담 없음), ⑵ 인스펙터에 항상 원본이 보여 디버깅이 쉽다(C의
> 최대 단점 회피). 대신 B의 알려진 위험인 **"곱하기를 빠뜨린 사용처"**는 구현 시 사용처를 한 번에
> 훑어 잡고, 가능하면 배율을 적용한 읽기 전용 프로퍼티 하나를 경유하도록 모아 둘 것.

⑵ **전역 버프를 어디에 둘 것인가.** 기존 매니저 구조(3장·2026-06-18 개편)에 이미
`UpgradeManager`(`MonoSingleton<T>`)가 있고 `lineSpeedMultiplier` / `robotAssembleMultiplier` /
`carSellPriceMultiplier` 같은 **전역 배율을 보관하는 역할을 이미 맡고 있다**.
→ `workerMoveSpeedMultiplier`, `workerAssembleMultiplier`, `workerConditionCostMultiplier` 등을
**`UpgradeManager`에 추가하는 것이 구조상 자연스럽다**(구매 차감은 기존대로 `EconomyManager.TrySpend`).
로봇팔 전역값을 모아둔 `StationConfig`와 대비되는 "사람 쪽 전역값"을 별도 `WorkerConfig`로 새로 파는
안도 있으나, 업그레이드 배율은 이미 `UpgradeManager`의 소관이므로 **분산시키지 않는 쪽을 권한다**.
개별 업그레이드 레벨은 작업자 인스턴스가 들고 있어야 하므로 `Worker` 자신에 두는 것이 맞다.

⑶ **열린 질문 — 사람에게 투자한 업그레이드는 자동화 전환 시 어떻게 되는가.**
8장이 정의한 최종 목표는 **전 라인 로봇팔 자동화**이고, 9-6의 7단계에서 공정 단위로 사람→로봇을 교체한다.
그렇다면 그 공정 작업자에게 쏟아부은 개별 업그레이드는 어떻게 처리되는가. 후보만 적어 두고 **결론은 내지 않는다**:
- **승계** — 그 작업자를 다른 공정으로 재배치하며 업그레이드를 그대로 가져간다(투자가 안 죽음. 단 "관리 번거로움
  회피"라는 자동화 동기가 약해질 수 있음).
- **소멸** — 로봇 전환 = 해고, 투자도 사라진다(전환 타이밍 자체가 의사결정이 되지만, 손실감이 크면
  유저가 전환을 미뤄 엔딩까지 못 갈 위험).
- **전환 보상** — 투자액의 일부를 재화나 로봇팔 할인으로 환급(중간 절충. 환급률이 곧 전환 페이싱 레버가 됨 —
  8장 리스크 1의 "전환 페이싱이 핵심"과 직결).
- 하위 질문: **전역 패시브 버프는 로봇팔에도 적용되는가?** 이동속도처럼 사람에게만 의미 있는 항목이 있어
  전역 버프 자체를 "사람 전용 / 전 설비 공통"으로 나눠야 할 수도 있다.

> **확정 (2026-08-20): 소멸.** 승계도 환급도 없다. 로봇팔로 전환하는 순간 그 공정 작업자에게 넣은
> 개별 업그레이드는 함께 사라진다.
> 유저 원문 — "사람 업그레이드 하고 로봇팔로 넘어가면 사람 업그레이드는 끝인거야."
> → 전환 타이밍 자체가 의사결정이 된다. 다만 위 후보 목록에서 지적한 **"손실감이 커 유저가 전환을
> 미룰 위험"**은 그대로 남으므로, 로봇팔 쪽 성능·무급여 이점이 그 손실을 확실히 덮도록 가격 설계를 할 것.
>
> **확정 (2026-08-20): 전역 패시브는 사람용 / 로봇용을 분리한다.** 하나의 전역 버프가 양쪽에 걸리지 않는다.
> 유저 원문 — "전역 패시브도 로봇팔과 사람도 달라."
> → 사람 전역 배율은 `UpgradeManager`의 `worker*` 계열에, 로봇 전역 배율은 기존 `robotAssembleMultiplier`
> 계열에 각각 둔다. 사람에게 쏟은 전역 투자도 자동화가 진행될수록 가치가 줄어들므로 "소멸" 결정과 결이 같다.

⑷ **열린 질문 — `forcedRestDuration`의 적정 범위는? → 확정 (2026-08-20): 기본값을 5초 → 10초로 상향.**

유저가 수치 판단을 위임했고, 아래 근거로 결정했다.

- 현재 **선제 휴식 3초 : 강제 휴식 5초 = 1.67배**뿐이다. 이 정도 차이로는 "미리 쉬게 해 두자"는
  유저 개입의 유인이 약하다 — 그냥 방치했다가 2초 더 쉬면 그만이기 때문이다.
- **10초로 올리면 3.3배**가 되어 선제 휴식이 확실한 이득이 된다. 9-7 ⑸에서 잡은 **선제/강제 비대칭**이
  비로소 실제 압박으로 작동한다.
- 특히 아래 ⑸에서 **인원 추가를 완전히 삭제**했으므로, 이 피로 압박이 **유저가 라인을 계속 주시할
  주요 동기**가 된다. 압박을 완화할 다른 수단이 없어진 만큼 압박 자체는 선명해야 한다.
- **레버는 절대값이 아니라 `선제 : 강제` 비율**이다. 튜닝할 때는 두 값을 따로 보지 말고 이 비율을
  기준으로 조정할 것(비율이 2배 아래로 내려가면 선제 휴식은 다시 무의미해진다).

> ✅ **코드 적용 완료 (2026-08-20).** `Assets/@Scripts/Comm/Object/Worker.cs`의
> `forcedRestDuration` 기본값이 **`5f` → `10f`**로 바뀌었고, 툴팁에 "선제 : 강제 비율이 레버"라는
> 근거(3초 : 10초 = 3.3배)를 함께 적어 두었다.
>
> ⚠️ **단, 씬에는 여전히 5가 직렬화되어 있다.** 이미 배치된 작업자(`Worker_01`, `RobotKyle`)는
> 코드 기본값을 따라가지 않으므로 **인스펙터에서 직접 10으로 바꾸거나 해당 필드 우클릭 → Reset**
> 해야 한다(직렬화된 씬 값이 코드 기본값보다 우선한다). 이후 새로 만드는 작업자는 10으로 생성된다.

⑸ **열린 질문 — 인원 추가를 완전히 막을 것인가? → 확정 (2026-08-20): 완전 삭제.**

> "인원추가는 완전히 없애. 이건 작업자가 한명이 하는게 더 낫고 유지보수 관리도 그게 더 나은거 같아."

- **체결 작업자는 공정당 1명 고정.** 인원 추가라는 개념 자체를 게임에서 뺀다("기본 성장 경로로 삼지
  않음" 수준이 아니라 삭제).
- 범위는 **공정마다 1명씩**이다 — 공장 전체에 1명이라는 뜻이 아니다. 공정이 늘면 체결 작업자도 그만큼 늘어난다.
- 이로써 9-14 서두에서 지적한 `TryAssignWork`의 인덱스 순회 문제(2명 이상이면 피로 압박이 무력화됨)가
  원천적으로 사라진다. `workers` 배열 구조 자체는 남겨 두더라도 **운용상 항상 1명**으로 간주한다.

> ⚠️ **이 결정은 체결 작업자에 한한다.** 아래 **9-15의 보급(재고 보충) 작업자는 증원이 가능하다** —
> 오히려 증원이 핵심 성장 수단 중 하나다. "인원 추가 삭제"를 공장 전체 규칙으로 오해하지 말 것.

**9-6 우선순위와의 관계 (이 절에서의 제안 — 기존 목록은 그대로 둔다)**

- 이 시스템은 **9-6의 4단계(인적 변수 — 피로도/휴식 + 품질 축 활성화) 직후**에 넣는 것이 맞다고 본다.
  업그레이드 대상 6개 중 4개가 **컨디션·품질 값**이라, 그 축이 실제로 압박으로 작동하기 전에는
  업그레이드해도 유저가 좋아진 걸 체감하지 못한다. "아픈 다음에 약을 판다"가 순서다.
- 다만 **3단계(경제 — 급여 고정비)보다 뒤여야 한다**는 점도 함께 본다. 업그레이드는 재화 사용처이므로
  수입·지출 구조가 먼저 서 있어야 가격을 정할 수 있다.
- 반대로 **7단계(자동화 전환 경제)보다는 반드시 앞**이어야 한다. 위 ⑶의 승계/소멸/전환 보상 결정이
  자동화 전환 경제의 입력값이기 때문이다.
- → 요약 제안: **기존 4단계와 5단계 사이에 "4.5단계: 작업자 업그레이드(개별 + 전역 패시브)"로 삽입**.
  기존 목록의 재배열은 하지 않고, 실제 착수 시점에 유저와 확정한다.

### 9-15. 재고 보급 시스템 — 체결/보급 역할 분리 (2026-08-20, 미구현 — 설계 결정만 확정)

9-14 ⑸에서 체결 작업자를 **공정당 1명 고정**으로 못 박았다. 그러면 재고는 누가 채우는가 —
이 절이 그 답이다. 유저 지시 원문을 먼저 그대로 보존한다.

> "채결 작업자는 채결만 하고, 재고 보충 전용 작업자가 채워주는 거야. 재고 보충 전용 작업자는 처음 시작부터
> 1명인데 이 작업자가 모든 공정을 채워주기에는 오래걸리니 유저 개입을 유도하는거야. 재고 보충 전용 작업자는
> 여러명 늘릴 수 있고, 추후 재고 보충 전용 작업자는 지게차 등 차량을 가지고 빠르고 많이 채울 수 있게 하는거지.
> 재고 보충 전용 작업자는 업그레이드 하면 이동속도를 빠르게 하거나, 재품을 가지고 다니는 개수가 많아져서
> 한번에 많이 채울 수 있거나 등등. 단, 모든 공정마다 각기 다른 재품으로 체결을 하기에 작업자가 한곳을 왔다가
> 채우면 다시 창고로 가서 필요 재품을 가지고 다른 공정으로 가야돼. 그리고 재고가 0이 되면 재고 보충 전용
> 작업자가 물품 채우는게 아니고 조금이라도 비면 작업자가 가서 채우려고 해서 계속 움직이는게 필요해."

**⑴ 역할 분리**

| 구분 | 체결 작업자 (`Worker` + `WorkerStation`) | 보급 작업자 (신규) |
| --- | --- | --- |
| 배치 | **공정 고정**, 공정당 **1명** (9-14 ⑸) | **공장 순회** — 특정 공정에 묶이지 않음 |
| 하는 일 | 체결만. 파일(`PartStack`)에서 집어 부착 | 보충만. 창고 → 공정 파일로 부품 운반 |
| 인원 | **증원 불가(개념 삭제)** | **증원 가능(유료)** — 초기 1명 |
| 성장 축 | `assembleSpeed` / 컨디션 / 품질 (9-14) | 이동속도 / 1회 운반 개수 / 차량 도입 |

- 이 분리가 좋은 이유 ⑴ **관리 대상이 명확히 나뉜다** — "이 공정이 느리다"는 체결 작업자 업그레이드로,
  "부품이 자꾸 떨어진다"는 보급 인원·속도로 푼다. 증상과 처방이 1:1로 붙어 유저가 무엇을 사야 할지 안다.
- ⑵ **각각 다른 업그레이드 축을 가진다** — 하나의 작업자가 체결도 하고 운반도 하면 업그레이드가
  섞여 "무엇에 투자해도 조금씩 좋아지는" 밋밋한 성장이 된다. 축을 갈라 두면 투자 판단이 선명해진다.
- ⑶ 9-14의 **피로 압박이 희석되지 않는다** — 체결 작업자가 왕복까지 하면 "쉬느라 멈춘 건지 부품 사러
  간 건지" 구분이 안 된다. 라인이 멈춘 이유가 항상 하나로 읽혀야 압박이 압박으로 작동한다.

**⑵ 핵심 제약 — 창고 왕복 강제**

- 공정마다 필요한 부품 타입이 다르다(`WorkerStation.targetPartTypes`, `PartStack.partType`).
  따라서 보급 작업자는 **한 번에 한 종류만** 운반한다.
- 한 공정을 채우고 나면 **반드시 창고로 돌아가** 다음 부품을 싣고 다른 공정으로 간다.
  공정 A → 공정 B로 곧장 가는 경로는 없다(들고 있는 부품이 B에 맞지 않으므로).
- 이 왕복이 곧 **병목의 정체**다. 보급 작업자를 늘려도 왕복 시간 자체는 줄지 않으므로,
  "인원 → 이동속도 → 적재량 → 차량"이라는 업그레이드 사다리가 각기 다른 방식으로 이 병목을 공략한다.
- 동시에 이 왕복이 **유저 개입이 존재할 이유**다. 왕복 대기 시간 동안 유저는 파일을 클릭해
  응급 보충하고(9-7 ⑴, `InputManager.refillAmount = 3`), 쿨타임이 걸리면 창고를 클릭해 초기화한다.
  즉 보급 작업자의 느림이 유저 조작의 가치를 만든다.

**⑶ 행동 규칙 — 재고 0을 기다리지 않는다**

- 유저 지시대로 **"조금이라도 비면"** 채우러 간다. 임계치가 `Count == 0`이 아니라 `Count < Capacity`다.
- 근거: **0에서만 반응하면 이미 라인이 멈춘 뒤라 늦다.** 창고 왕복에 시간이 걸리므로 0을 감지한 시점에
  출발하면 도착할 때까지 그 공정은 확정적으로 정지한다. 보급은 본질적으로 **선제 행동**이어야 한다.
  (9-7 ⑸의 "선제 휴식 vs 강제 휴식" 비대칭과 같은 사고방식 — 미리 움직이는 쪽이 이득이어야 한다.)
- 부수 효과 ⑴ **연출**: 보급 작업자는 사실상 항상 움직이는 상태가 기본이 되어 공장이 살아 있어 보인다.
- 부수 효과 ⑵ **압박**: "작업자가 쉬지 않고 일하는데도 계속 부족하다"는 그림이 만들어진다.
  놀고 있는데 부족한 것보다 **일하는데도 모자란** 쪽이 증원·업그레이드 구매 동기로 훨씬 강하다.

**⑷ 초기 인원 1명 → 증원 가능**

- 시작은 **1명**. 1명으로 모든 공정을 감당할 수 **없게** 설계하는 것이 의도다(유저 지시 명시).
  감당 가능하면 유저가 화면을 볼 이유가 사라진다 — 방치형이 아니라 무관심 게임이 된다.
- 증원은 **유료**. 다만 증원만으로 전부 해결되면 9-14에서 기각한 "인원 = 압박 제거 버튼" 문제가
  보급 쪽에서 재현되므로, **증원 비용은 누진**으로 두고 후반 해법은 차량 단계로 넘기는 것이 맞다.
- 급여(9-3, 9-6 3단계)가 들어오면 보급 인원은 곧 **고정비**가 되어, 무작정 늘리는 선택에 자연스러운
  제동이 걸린다 → 증원/업그레이드/차량 사이의 의사결정이 성립한다.

**⑸ 보급 작업자 업그레이드 축**

| 축 | 개별 / 전역 | 효과 | 비고 |
| --- | --- | --- | --- |
| **이동속도** | 개별 + 전역 패시브 | 왕복 시간 단축 = 순회 주기 단축 | 9-14의 전역 패시브(사람용)와 같은 계열로 묶을 수 있음 |
| **1회 운반 개수** | 개별 | 한 번에 채우는 양 증가 = 왕복 **횟수** 감소 | 아래 열린 질문(`capacity` 12와의 관계) 참조 |
| **차량 도입(손수레 → 지게차 등)** | 개별(단계형) | 속도·적재량을 **대폭** 상승 | 9-6 8단계 "손수레 → 지게차"와 같은 축 |

- 이동속도는 왕복 **시간**을, 운반 개수는 왕복 **횟수**를 줄인다 — 서로 다른 변수를 건드리므로
  둘 다 사는 것이 최적이 되고, 어느 쪽이 급한지가 라인 상태에 따라 달라진다(= 의사결정).
- **차량 단계는 성장 체감 장치이기도 하다.** 사람이 부품을 안고 뛰던 그림이 지게차가 팔레트를 싣고
  달리는 그림으로 **눈에 보이게** 바뀐다. 숫자만 오르는 업그레이드와 달리 화면이 변해 성장이 각인된다
  (8장 진단의 "피드백 빈약" 회수 지점이기도 하다).

**⑹ 기존 시스템과의 접점 (현재 구현된 코드 기준)**

| 기존 요소 | 현재 동작 | 보급 시스템이 붙는 지점 |
| --- | --- | --- |
| `PartStack` | 공정 재고 파일. `capacity` 기본 **12**, `Count`/`Capacity`/`IsEmpty`/`IsFull`/`Fill` 노출. 아래부터 차고 **위부터 소모**(`BuildFillOrder`/`TopSlotIndex`) | 보급 작업자는 도착 후 **`Add(int amount)`** 호출(용량 초과분은 버려지고 실제 추가분 반환). 대상 선정은 `Fill` / `IsFull`을 읽어 판단 |
| `PartStack.TryConsume()` | 체결 시 1개 소모, 재고 0이면 `false` | 소모 속도가 곧 보급 수요. 우선순위 규칙의 입력값이 된다 |
| `PartStack.SetPartType(PartType)` | `WorkerStation`이 공정 타입에 맞춰 지정 | 보급 작업자가 **어떤 부품을 실을지**는 이 `partType`을 그대로 읽으면 된다 |
| `WorkerStation` | `targetPartTypes[]` / `partStacks[]` / `workers[]` 보유. `IsBlockedByStock()`로 재고 때문에 막혔는지 판단 | 보급 대상 공정 목록 = 씬의 `WorkerStation` 집합. `IsBlockedByStock()`이 `true`인 공정은 **최우선 긴급** 신호로 쓸 수 있다 |
| `InputManager` | 파일 클릭 시 `refillAmount = 3` 적립, `refillCooldown = 8f` **전역** 쿨타임, `warehouse` 클릭으로 쿨타임 즉시 초기화(`CanRefillNow`/`RefillCooldownRemaining`) | 유저의 **응급 보충**. 보급 작업자와 같은 `PartStack.Add`를 쓰므로 시스템은 이미 호환된다 — 남은 건 밸런스(열린 질문 참조) |
| `warehouse`(`InputManager.warehouse`) | 지금은 **쿨타임 초기화용 클릭 대상**일 뿐 | 보급 작업자의 **왕복 기점**이라는 실체를 갖게 된다. 창고가 화면상 의미 있는 장소가 된다 |

- 신규로 필요한 것은 **보급 작업자 본체(순회 상태기계)** 와 **대상 선정 규칙** 정도이며,
  재고 조작 API(`Add`/`Count`/`Fill`)는 이미 있는 것을 그대로 쓴다 = 기존 구조에 얹는 확장이다.

**⑺ 9-6 우선순위와의 관계 — 2단계(물류 1단계)가 이 설계로 대체된다**

기존 9-6 목록은 **재배열하지 않는다.** 다만 2단계의 내용은 아래로 바뀐다.

- 기존 서술: *"물류 1단계 — 공정 작업자의 창고 왕복 → 전담 보급 작업자 고용 + 인원 상한"*
- **변경 후**: **체결 작업자의 창고 왕복은 폐기**한다(체결 작업자는 공정에 고정되어 체결만 한다).
  즉 "공정 작업자의 왕복" 단계를 거치지 않고 **처음부터 전담 보급 작업자만** 존재한다.
- **인원 상한은 체결 작업자가 아니라 보급 작업자에 적용된다.** 체결 작업자는 상한이 아니라
  **공정당 1명 고정**이므로 상한이라는 개념 자체가 성립하지 않는다(9-14 ⑸).
- 8단계(물류 2단계 — 손수레 → 지게차)는 그대로 유효하며, 위 ⑸의 **차량 도입 축**이 그 단계에 해당한다.

**⑻ 열린 질문 (다음에 확정해야 할 것)**

1. **보급 우선순위 규칙** — 어느 공정부터 채우는가? 후보: ⓐ 가장 적게 남은 곳(`Fill` 최소),
   ⓑ 가장 가까운 곳(이동거리 최소), ⓒ 소모 속도가 빠른 곳, ⓓ 가장 오래 방치된 곳.
   **이 규칙이 체감 난이도를 좌우하는 핵심 레버다** — ⓐ는 라인 정지를 잘 막지만 동선이 튀어 비효율적이고,
   ⓑ는 효율적이지만 먼 공정이 상습적으로 굶어 유저 개입 지점이 한쪽으로 쏠린다.
   `WorkerStation.IsBlockedByStock()`이 `true`인 공정을 무조건 최우선으로 끼워 넣을지도 함께 결정.
   > **확정 (2026-08-20): ⓐ 가장 적게 남은 곳 우선(최소 잔량 우선).**
   > 근거는 효율이 아니라 **가독성**이다. 규칙이 유저 눈에 보여야 "쟤가 저기 가 있으니 여긴 내가
   > 클릭해야겠다"는 판단이 선다 — 유저 개입이 감이 아니라 **읽기**가 되어야 한다.
   > ⓑ 최단거리 우선은 먼 공정이 상습적으로 굶고, ⓒ 소모속도 우선은 똑똑하지만 유저가 규칙을
   > 읽어낼 수 없어 개입 지점을 고르지 못한다.
   > ⚠️ **아직 미정(구현 시 확정)**: ⑴ **동률일 때 무엇으로 가르는가**(거리? 방치 시간?),
   > ⑵ **`IsBlockedByStock()`(이미 라인이 멈춘 공정)을 최우선으로 끼워 넣을지.**
2. **창고 재고는 무한인가** — 창고에서 무한정 꺼내 쓰는가, 아니면 창고 자체도 외부 납품 등으로
   보급이 필요한가. 후자면 **보급 계약·납품 주기**라는 경제 레이어가 하나 더 생긴다(스코프 주의).
   > **확정 (2026-08-20): 창고 재고는 무한.** 창고 자체를 보급하는 층(외부 납품 등)은 두지 않는다.
   > 보급을 순수하게 **시간·동선 문제**로 유지해 압박의 정체를 하나로 묶는다 — 창고가 비어서 못 채우는
   > 상황까지 끼면 "왜 안 채워지는지"가 두 갈래가 되어 위 1번의 가독성 원칙이 무너진다.
   > 단, **후반 컨텐츠로 창고 유한화를 나중에 검토할 여지**는 남겨 둔다.
3. **1회 운반 개수 초기값과 `PartStack.capacity`(12)의 관계** — 초기값이 12 미만이면 한 공정을
   가득 채우려고 **같은 공정을 여러 번 왕복**하게 된다. 이것이 의도된 압박인지, 아니면
   "한 번 가면 가득 채운다"를 기본으로 두고 왕복 **횟수**가 아닌 **공정 수**로 압박을 만들지 결정 필요.
   > **확정 (2026-08-20): 1회 운반 개수 초기값 = 6.** `PartStack.capacity`(12)의 **절반**이라
   > 한 공정을 가득 채우려면 **2회 왕복**이 필요하다. 이 답답함이 **의도된 압박**이다.
   > 동시에 이것이 운반 개수 업그레이드의 **첫 번째 체감 지점**이 된다 — **6 → 12가 되는 순간
   > 왕복이 절반**으로 줄어, 성장이 숫자가 아니라 동선의 변화로 보인다.
4. **보급 작업자에게도 컨디션·피로가 있는가** — 체결 작업자와 동일 규칙(`conditionCostPerCar`,
   선제/강제 휴식)을 적용할지, 아예 없는지. 있으면 관리 대상이 두 배가 되어 번거로움이 커지고
   (= 자동화 동기는 강해지고), 없으면 보급은 순수 처리량 문제로 단순해진다.
   > **확정 (2026-08-20): 보급 작업자는 컨디션·피로가 없다.** 관리 대상을 늘리지 않는다.
   > 피로는 **체결 작업자만** 갖고, 보급 작업자의 제약은 **이동 시간과 적재량**이다.
   > 설계상 깔끔한 이유 — 두 직군의 병목이 **서로 다른 종류**가 된다. 체결은 *얼마나 오래 버티는가*
   > (지속력), 보급은 *얼마나 빨리·많이 나르는가*(처리량). 증상이 겹치지 않으므로 유저는 라인을 보고
   > 어느 쪽 문제인지 즉시 구분할 수 있고, 두 직군의 업그레이드 축도 서로 잠식하지 않는다.
5. **유저 클릭 응급 보충(+3, 쿨타임 8초)과 보급 작업자의 관계** — 클릭이 보급을 **대체**하는가
   **보조**하는가. 대체면 보급 작업자를 살 이유가 줄고, 보조면 +3과 쿨타임 8초의 수치가
   보급 작업자 1명의 처리량 대비 어느 정도여야 하는지 밸런스를 잡아야 한다.
6. **보급 작업자의 경로/충돌 처리** — 라인과 차량을 가로질러 다니는가, 통로를 따라 다니는가.
   9-6 8단계의 "통로/경로탐색 + 라인 레이아웃 의사결정"과 어디까지 겹치는지 경계 확정 필요.
7. **`workers[]` 배열 구조를 그대로 둘 것인가** — 9-14 ⑸로 체결 작업자는 항상 1명이 되었으므로,
   `WorkerStation.workers`를 단일 참조로 바꿀지 배열을 남길지(보급 작업자와의 코드 공유 여부 포함) 결정 필요.
